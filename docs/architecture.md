# アーキテクチャ

VR SNS (Resonite / VRChat 類似) の実現可能性を探るプロトタイプ。
**最初のゴールは「複数ユーザーが同時にアクセスできる 3D 空間」** であり、それ以外は意図的にスコープ外とする。

## 1. 方針

- **簡素さ最優先**。プロトタイプなので、認証・永続化・スケールアウト・最適化は行わない。
- **ブラウザだけで動く** (Three.js / React Three Fiber)。WebXR は後続フェーズで追加する。
- **サーバーは薄いリレー**。ワールドの状態は「接続中ユーザーの姿勢」と「置かれたオブジェクト」だけを持つ。
- クライアント / サーバー間で **型を共有** し、プロトコルの不整合を防ぐ。

## 2. スコープ

### 今回の対象 (M0〜M4)

| 項目 | 内容 |
|---|---|
| 3D 空間 | 床・簡単なオブジェクトがあるだけの 1 ワールド |
| 入室 | 表示名を入力して入室 (認証なし) |
| 移動 | デスクトップ操作 (WASD + マウス視点) |
| アバター | 色付きの簡易アバター (胴体 + 頭) + 名前表示 |
| 同期 | 全ユーザーの位置・向きをリアルタイム表示 |
| 画像の配置 | 画像ファイルをドラッグ&ドロップして 3D 空間に置く。画像本体は IPFS (CID) で共有し、全員に同期される |
| ファイルの配置 | 任意のファイルをドロップして、ファイルの形のアイコンとして 3D 空間に置く (音声・映像は専用のアイコン)。コンテキストメニューからダウンロードできる |
| オブジェクト操作 | 画面中央のカーソルで画像を狙い、右ボタンでつかんで動かす (全員に同期。つかんでいる間は排他)。中ボタンのリングメニューから削除・複製 |

### 対象外 (後続)

WebXR / VR コントローラ、ボイスチャット、glTF・VRM アバター、ファイルの中身のプレビュー・再生、画像以外のワールド内編集
(画像の回転・拡大縮小、元に戻す、操作の権限管理を含む)、ユーザーアカウント、永続化、複数ルーム、物理演算、チャット。

## 3. 全体構成

```mermaid
graph LR
    subgraph Browser A
        CA[client<br/>Vite + R3F + Helia]
    end
    subgraph Browser B
        CB[client<br/>Vite + R3F + Helia]
    end
    subgraph Server
        S[server<br/>Node.js + ws]
        H[Helia ノード<br/>libp2p ws / circuit relay / pin]
    end

    CA <-->|WebSocket / JSON<br/>姿勢・配置・ピア ID| S
    CB <-->|WebSocket / JSON| S
    CA <-->|libp2p WebSocket<br/>bitswap| H
    CB <-->|libp2p WebSocket<br/>bitswap| H
    CA <-.->|WebRTC (直接)<br/>bitswap| CB
```

- クライアントは自分の姿勢を一定間隔でサーバーに送る。
- サーバーは全員の姿勢をまとめて (スナップショット) 一定間隔で全員に配信する。
- クライアントは受信した他人の姿勢を補間して描画する。自分自身はローカルで即時反映する。
- 画像は IPFS で共有する。ワールドの同期 (WebSocket) には CID だけを載せ、画像本体は libp2p の bitswap で取得する。
  取得元は、サーバーの Helia ノード (常に接続・pin 済み) と、直接つながった他のブラウザ (WebRTC)。

## 4. 技術選定

| 領域 | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | client / server / 共有型を統一 |
| パッケージ管理 | pnpm workspace | 共有パッケージを簡単に扱える |
| クライアント | Vite + React + three + @react-three/fiber + @react-three/drei | 宣言的な 3D、開発サイクルが速い |
| XR (後続) | @react-three/xr | WebXR のラッパー |
| サーバー | Node.js + `ws` | WebSocket のみ必要。フレームワーク不要 |
| メッセージ形式 | JSON | デバッグ容易。必要になったらバイナリ化 |
| 画像の共有 | IPFS ([Helia](https://github.com/ipfs/helia) 7 + libp2p) | 画像を内容アドレス (CID) で扱い、ブラウザ同士 (WebRTC) でも配れる |

> Node / pnpm のバージョンは実装着手時に確認して `package.json` の `engines` に記載する。

## 6. コンポーネント責務

### server (`apps/server`)

- WebSocket 接続を受け付け、接続ごとにユーザー ID を採番する。
- `join` を受けたらユーザーを登録し、`welcome` を返し、他者へ `peer_joined` を通知する。
- 受信した `pose` を最新値としてメモリ上に保持する。
- 一定間隔 (20Hz) で全ユーザーの姿勢を `snapshot` として配信する。
- 切断時にユーザーを削除し、`peer_left` を通知する。
- 同じプロセスで Helia (IPFS) ノードを動かす。libp2p の WebSocket で待ち受け (既定 8081)、ブラウザの接続先 (bootstrap) と circuit relay (ブラウザ同士の接続の仲介) を兼ねる。
- `place_image` を受けたら、CID の中身を IPFS から取得して検証 (サイズ上限・画像形式をマジックナンバーで判定) し、pin してから `object_added` を全員に通知する。
  pin しておくので、置いた人が退室した後も画像を配り続けられる。
- `ipfs_peer` を受けたら、本人以外に `peer_ipfs` で libp2p ピア ID を知らせる (ブラウザ同士の直接接続用)。
- `grab_object` / `move_object` / `release_object` / `delete_object` / `duplicate_object` を受けて、オブジェクトの状態 (位置・向き・つかんでいる人) を更新し、
  `object_updated` / `object_removed` / `object_added` を配る。つかんでいる間は本人だけが動かせる (排他)。つかんだまま切断したら自動で離す。
- 入力値の最低限の検証 (型・数値範囲・名前の長さ) のみ行う。

### client (`apps/client`)

- 入室画面 (名前入力) → 3D シーン。
- ローカルプレイヤーの入力処理と移動 (クライアント権威)。
- 自分の姿勢を 20Hz で送信。
- 他ユーザーのアバターを `snapshot` から生成・更新・削除し、補間表示する。
- ブラウザ内で Helia ノードを動かし、サーバー (と他のブラウザ) に接続する。
- 画像ファイルのドロップを受け付け、ドロップ位置の床に置く (IPFS に追加 → CID を `place_image` で送る)。
- ワールドのオブジェクト (画像) を CID で IPFS から取得して描画する。
- 画面中央をカーソルにしてオブジェクトを狙い、右ボタンでつかんで運び、中ボタンのリングメニューから削除・複製する。

### protocol (`packages/protocol`)

- client / server 間のメッセージ型と定数 (送信間隔など) を定義する。

## 7. 設計上の判断

| 判断 | 内容 | 理由 / トレードオフ |
|---|---|---|
| クライアント権威の移動 | 自分の位置はクライアントが決めて送信 | 実装が簡単。チートは許容 (プロトタイプ) |
| スナップショット配信 | 差分でなく全員分を毎回送る | 実装が単純。人数が少ない前提で帯域は問題にならない |
| 1 ワールド・1 ルーム | ルーム ID を持たない | スコープ削減。将来はルーム ID をメッセージに追加 |
| 認証なし | 表示名のみ | プロトタイプの目的外 |
| 永続化なし | サーバー再起動で状態は消える (置かれた画像も) | 同上 |
| 画像は IPFS で共有 | WebSocket (JSON, 4KB 上限) には載せず、CID だけを送る。画像本体は bitswap で取得する | 大きなバイナリでリアルタイム同期を詰まらせない。内容アドレスなので改ざんできず、同じ画像は同じ CID になる |
| サーバーが検証して pin | `place_image` の CID をサーバーが取得・検証 (サイズ・形式) してから配置する | 不正なデータを全員に配らない。置いた人が退室しても画像が残る (サーバーが常駐の提供元になる) |
| つかみは排他ロック | つかんでいる間は、つかんだ本人の `move_object` だけを受け付ける。他の人はつかめず、削除もできない。切断で自動解除する | 同時に動かされてオブジェクトが飛び回るのを防ぐ。ロックが固まらないよう、切断時に必ず解放する |
| 保持は参照カウント | 同じ中身 (CID) を指すオブジェクトが複数あっても 1 つだけ保持し、最後の参照が消えたら unpin + gc で解放する。合計は上限 (既定 20 GiB) | ディスクを使い切らない。複製・同じファイルの再投入で容量が増えない。削除でディスクが戻る |
| 大きなファイルは、ブラウザにコピーを作らない | アップロード中のファイルは、ブロックを保存せず、サーバーが取りに来たら元のファイルから直接読んで渡す。ダウンロードで取得したブロックも保存しない | IndexedDB は遅く (1MiB あたり 0.2〜0.3 秒) 転送が止まり、メモリに保存するとファイルのサイズ分のメモリを使う。コピーを作らなければ、どちらも要らない |
| 大きなファイルは、置いたあと、サーバーがバックグラウンドで取得する | 16MiB を超えるファイルは、宣言サイズと先頭だけを調べて先に置き (`stored: false`)、続けてサーバーが全部を取得して保持する。取り終えるまで、置いた人のブラウザが配る。ダウンロードする人は、先に直接取得を試し、だめなら `request_file` で取得の完了を待つ | 置いた人が、いつ退室するか分からないので、早く保持したい。2 GiB の取得は約 1 分かかるので、待たずに置く。代わりに、取り終えるまでは置いた人がタブを開いておく必要があり、途中で退室すると「オフライン」になる |
| サイズと種類はサーバーが決める | `size` はサーバーが実際に取得したバイト数、`category` (アイコンの種類) は名前と先頭バイトから判定する。クライアントの申告は使わない | 表示や容量の計算を偽られない |
| つかんだ物は手元で動かす | つかんでいる本人は手元の位置をそのまま使い、サーバーからの echo は受けない。他の人には 20Hz で配り、受け取った側が補間する | 操作の遅れをなくし、20Hz の更新でも滑らかに見せる |
| ブラウザ同士は WebRTC で直接接続 | 入室後に libp2p ピア ID を共有し、既存の参加者が新しい参加者へ中継 (circuit relay) 経由で WebRTC 接続する | サーバーの負荷と単一障害点を減らす。通らない環境ではサーバー経由で取得できる |

## 8. 想定する制約・リスク

- WebSocket (TCP) は遅延・ジッタに弱く、人数が増えると限界がある。まずは数人〜十数人を想定する。
  将来的に WebRTC DataChannel / WebTransport への移行を検討する。
- 状態同期の見た目の品質は補間実装に依存する (`design.md` 参照)。
- WebXR 対応は端末・ブラウザ依存が大きい。デスクトップ操作は常に併存させる。
- IPFS (libp2p) の制約:
  - **安全なコンテキストが必須**: Helia / libp2p は Web Crypto (`crypto.subtle`: 鍵のインポート・生成・署名・ダイジェスト) を使う。
    ブラウザはこれを HTTPS か `localhost` にしか提供しないため、`http://<LAN の IP>` で開いたページでは IPFS を起動できない
    (`crypto.subtle` が undefined になる)。`digest` だけを補っても `importKey` などで失敗するため、フォールバックは設けていない。
    クライアントは起動前にこれを検出して HUD に原因を表示する。対処は README を参照 (localhost へのポート転送、開発用の許可設定、HTTPS)。
  - ブラウザから接続できるのは WebSocket / WebRTC のみ。現状は平文の `ws://` で接続するため、`https://` で配信するページからは混在コンテンツとして拒否される。
    HTTPS 化するにはページ・ワールド同期 (8080)・libp2p (8081) のすべてを TLS (`wss://`) にし、ドメインと証明書が必要になる。
  - ブラウザ同士の直接接続 (WebRTC) には STUN が必要で、NAT が厳しい環境では TURN の中継が必要になる。
    VPS に coturn を置き、サーバーが入室ごとに時間制限つきの認証情報 (TURN REST API) を配る。TURN が使えない環境 (3478 が通らないなど) でも、サーバー経由 (bitswap) で画像は取得できる。
    TURN は TLS (5349 / 443) に未対応で、認証情報は入室した誰にでも配られる。
  - 中継の予約は切断しても有効期限 (2 時間) まで残る。ブラウザはページを開くたびに新しいピア ID になるため、
    予約の上限を 1000 に引き上げている (既定は 15)。
  - サーバーのブロックストアはディスク。起動のたびに空にするので、再起動すると置いた画像・ファイルは消える。
- 任意のファイルを誰でもアップロードできる (1 個 2 GiB、合計 20 GiB まで)。
  16MiB 以下のファイルは、置いた人が退室しても、削除されるかサーバーが再起動するまで、サーバーが保持して配り続ける。公開範囲に注意すること。
  16MiB を超えるファイルは、置いたあと、サーバーが取得を終えるまで (2 GiB で約 1 分) は、置いた人のタブが配る。それまでに置いた人が退室すると、そのファイルは取得できない (オフライン)。
